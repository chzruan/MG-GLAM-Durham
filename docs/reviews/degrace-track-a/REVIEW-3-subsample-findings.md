# REVIEW 3: hashed quantised particle subsample (I9) — findings

Branch `degrace-track-a` vs `cz` (merge base 69c9261). Scope: `PMP2mod_subsample.f90`,
`glam_hash.c`, the `glam_hash.o` makefile rules, the `WriteSubsample` hook in
`PMP2mod_analyze.f90`, `test/extras/{test_subsample.f90,hash_ref.c,check_subsample.py,run_subsample_test.sh}`
and `read_subsample` / V6 in `test/precise_z/asserts.py`. Read-only review, 2026-10-17;
nothing was built or run except two Python arithmetic snippets.

## 1. Summary

The hash, selection rule, two-pass compaction, quantisation, int16 encoding, C interop,
64-bit kinds, stream layout and velocity epoch are all correct, and the unit test compares
the writer against the raw input arrays and an independent numpy transcription of the rule
(whose constants I checked against the published splitmix64 vectors). Output order is fixed
by particle index, which GLAM never permutes (MOVE, checkpoints, BDM restore, Analysis).
The one substantive problem is what that index *means*: the module and the `.meta` claim
"ID = index-1 in lattice order" and print the PMP2start formula (x fastest), but the
production ICs come through `ic2pm`, which ignores the Gadget ID block; Baojiu's 2LPTic
files are z-fastest, and the AGENTS.md-default FML generator writes neither ID order
(z-fastest lattice loop vs x-fastest IDs) nor even lattice order when run on >1 MPI rank
(swap-with-last compaction in `communicate_particles`). Selection stays reproducible across
twins, threads and restarts, but the stated purpose "Lagrangian positions from the ID" is not
deliverable from the files as written, and a reader following the `.meta` gets wrong
Lagrangian positions silently. Recommendation: **ready after the listed fixes** (M1 before
any Lagrangian use of the product; the Minors are test-strength and spec items).

Counts: Blocker 0, Major 1, Minor 4, Nit 6.

## 3. Verified OK

- **Hash.** `glam_hash.c:22-28` uses the published splitmix64 constants `0x9E3779B97F4A7C15`, `0xBF58476D1CE4E5B9`, `0x94D049BB133111EB` and shifts 30/27/31; the numpy transcription in `check_subsample.py:37-44` is identical in effect and reproduces the published test vectors (splitmix64(0) = E220A8397B1DCDAF, splitmix64(1) = 910A2DEC89025CC1, checked with a Python snippet).
- **Selection rule.** `splitmix64(ID ^ SALT) % M == 0` evaluated in `uint64_t` (C) and `np.uint64` (Python) — unsigned, no sign issue; modulo bias is `(ceil(2^64/M)/2^64 - 1/M)` ~ 5e-18 at M = 100. SALT `0x5EED00DE6C0A2026` < 2^63, so the `int(z'...', c_int64_t)` constant is exact and the int64/uint64 by-value pass preserves the bit pattern; M = 1 short-cuts in the block routines agree with `glam_select`.
- **C interoperability.** The four `bind(C)` interfaces match the prototypes: `Integer(c_int64_t), value` <-> `uint64_t`/`int64_t`, `Integer(c_int)` <-> `int`, `Integer(c_int32_t) :: idx(*)` <-> `int32_t *`; `glam_select_indices` writes `(int32_t)i` with `i < n <= SubChunk <= 2^31-1`, enforced at `PMP2mod_subsample.f90:100`.
- **Integer kinds / 2048^3.** `Nparticles` is `Integer*8` in Tools; `Nchunk, nsel, ic, id0, n, k, j, i, iq, o, cnt, off, nclip, nbad, c0, c1, cr` are all `Integer*8`; C counters `int64_t`; meta `N_p`, `n_sel` printed with `i20`; Python uses int64/uint64; OpenMP loop variables are 64-bit. The only 32-bit quantities are within-chunk offsets (bounded) and `Msub`, `moment`, component index.
- **Deterministic compaction.** Pass 1 counts per fixed chunk, serial exclusive prefix sum, pass 2 writes disjoint slot ranges `off(ic-1)+1 .. off(ic)` in increasing ID within each chunk; result independent of thread count, schedule and `SubChunk`; no floating-point reductions, so bitwise reproducible. Tested: 1 vs 4 threads bitwise on all files, 33 chunks (`SubChunk = 1000`, partial last chunk) vs 1 chunk bitwise. The two-pass count mismatch guard (`nbad`) stops the run rather than overrunning `q`.
- **Position quantisation.** `s = x - 1` (grid units from 0), wrapped with `modulo(s, N)`, `iq = int(s*65536/N, 8)` (floor for s >= 0), clamped to `[0, 65535]` (handles `modulo` returning exactly `N` by rounding), stored `iq - 32768` in `[-32768, 32767]`. Decode `(q + 32768 + 0.5) Box/65536` is written identically in the `.meta`, `check_subsample.decode` and `asserts.read_subsample` — exact inverse; `dx = Box/65536` = 15.6 kpc/h at Box = 1024 as claimed. The Python reference (`np.mod`, `floor(s*(NQ/ngrid))`, `minimum(.., NQ-1)`) follows the same double-precision path. Edge cases in the driver (x = 1, 65, 0.5, largest real*4 below 65 -> q = 65535 confirmed, half box, one quantum) are all in the M = 1 file, so they are exercised.
- **Velocity quantisation.** `v = V_code * 100 Box/NGRID / a_v` km/s (GLAM `V = v_pec a NGRID/(100 Box)`, cf. `ic2pm.f90:75-76`), `s = anint(v/0.25)` in real*8 (no integer overflow), clipped to +-32767 = +-8191.75 km/s, -32768 never produced; per-component and summed clip counts in the `.meta` and console; Python reference reproduces `rint`, clipping and counts; `dv_quant = 0.25` asserted.
- **Velocity epoch.** In the main loop (`PMP2main.f90:52-71`) `ASTEP` is set to the step about to be taken (exact-z: `dAlist(ISTEP+1)`; legacy: `1.5*ASTEP`) *before* `MOVE`; `ADDTIME` (`:476-481`) then increments `ISTEP` and sets `AEXPN`; `Analysis` follows. So at the hook `ASTEP` is the step just taken and `AEXPN - ASTEP/2` is the leapfrog velocity epoch, the same expression and conversion factor `100 Box/NGRID/a_v` as `MomentumDeposit` (`PMP2mod_extras.f90:461,531`); `a_v`, `a_x` and `v_scale` are recorded in the `.meta`. Restart path: `SetExactSteps` restores `ASTEP = dAlist(ISTEP)` (last executed step), consistent.
- **Stream layout / endianness.** Planar `qx, qy, qz, vx, vy, vz`, each `n_sel` int16, written through `access='stream'` with `convert='little_endian'`, which overrides the makefile's `-convert big_endian`; the unit test compiles with the production `FFLAGS` (including `-convert big_endian`) and the Python reader uses `'<i2'`, so a byte-order error would fail check b. Blocked 256 MB writes.
- **Index order is never permuted in GLAM.** `MOVE` reads `XPAR(IN)`/`VX(IN)` (`PMP2main.f90:709,712`) and writes them back at the same index (`:887,890`), in place; no sort/swap/permutation in `PMP2main.f90`, `PMP2mod_tools.f90`, `PMP2mod_density.f90`, `PMP2mod_power.f90`, `PMP2MG_subroutines.f90`, `PMP2MGsolver_fR.f90` (`git grep`); no in-place writes to the particle arrays in power/density/analyze before the hook; `WriteDataPM`/`ReadDataPM` page in index order (`Xb(j0-jfirst+1) = Xpar(j0)`, `Xpar(ip+ioff) = Xb(ip)`); BDM moves the arrays aside with `move_alloc` in `RescaleCoords` and restores the identical arrays in `RemoveBuffer` (`PMP2linker.f90:539-541, 2154-2156`), buffer images are appended after the first `Nparticles` rows; `ParticlesRandom` (iDumpPart) copies into `Xb` without permuting. The subsample hook (`PMP2mod_analyze.f90:132`) runs before iDumpPart, Bias and BDM (`:202`). `ic2pm` fills `XPAR(ioff+j)` in file order (`ic2pm.f90:253-268`). The PMP2start formula in the module header matches `PMP2start.f90:398`.
- **Hook and lifecycle.** `iExtra == 1 .and. SubM > 0 .and. OutClass == 1`; `Msub <= 0` returns; `newunit=` (no unit-number collisions); `status='replace'` makes a replayed output step after a restart rewrite identical files; `q`, `cnt`, `off`, per-thread `idx` deallocated; `.meta` keys parse with both readers (first `=`/` = ` split; comments after values carry no key-breaking effect).
- **makefile.** `CC = icx`, `CFLAGS = -O2 -g -march=core-avx2 -mcmodel=medium`, explicit `glam_hash.o: glam_hash.c` rule; `PMP2mod_subsample.o` and `glam_hash.o` inserted after `PMP2mod_extras.o` and before `PMP2mod_power.o`/`PMP2mod_analyze.o` in `OBJ`, `PMP2MG` and `PMP2spectrum` (module order Tools -> ... -> Subsample -> Power -> Linker -> Analyze holds for a serial make); `PMP2start` does not link Analysis and correctly omits Subsample; `clean` removes `*.o`; `test/extras/work/` is in `.gitignore`.
- **Test quality.** `run_subsample_test.sh` really tests 1e7 IDs (`NHASH=10000000`: 5e6 sequential, 5e6 xorshift64* full-range, plus 0, 2^63-1, 2^63, 2^64-1 and SALT); `check_subsample.py` compares the files against the raw float32 arrays dumped by the driver *before* `WriteSubsample` (independent of the writer) at the Python-selected IDs, so a wrong hash, wrong order, wrong scale, wrong endianness or off-by-one would fail; M = 0 writes nothing (checked); failures propagate via `report`/`nfail`, build failures exit 2, missing `hash_ref.bin` is a FAIL not a skip; memory ~180 MB; `.o/.mod/hash_ref.bin` removed at the end.
- **Storage / cost.** M = 100: 8.59e7 x 12 B = 1.03 GB (2048^3), 1.07e7 x 12 B = 0.129 GB (1024^3), matching plan §9; M = 1: 103 GB per output at 2048^3 with a transient `q` of 17.2 GB per component. Hash evaluated 7 times over N_p (count + 6 components): ~6e10 splitmix64+mod at 2048^3, roughly 10 s per output on 64 threads — acceptable; per-thread scratch 4 MB.
