# REVIEW 1: snapshot, subsample, schedule and PowerDM readers against the Fortran writers

Branch `glamio-readers`, commit 0a6ecff, reviewed 2026-10-18 against `cz`.
Scope: `python/glamio/snapshot.py`, `subsample.py`, `schedule.py`, `powerdm.py`
and the parts of `product.py` they use, read line by line against
`PMP2mod_tools.f90` (Tools declarations, `ReadDataPM`, `WriteDataPM`),
`PMP2main.f90` (main loop, `ADDTIME`, `MOVE`, `SetExactSteps`),
`PMP2mod_subsample.f90` + `glam_hash.c`, `PMP2mod_extras.f90`
(`WriteOutputSchedule`), `PMP2mod_power.f90` (`GetPower`), `ic2pm.f90`,
`PMP2start.f90` (`FilesWrite`), `makefile`. Read-only; Python checks with the
cosemu interpreter on the real outputs of case10/case11/case12 and the LCDM
pilot (schedule, 84 PowerDM files). All line numbers below are of the
`glamio-readers` checkout.

## 1. Summary

The four readers reproduce the Fortran layouts, units and epochs exactly. The
strongest evidence is bit-exact: re-quantising every PMcrs particle of
case11 step 70 with the Fortran `WriteSubsample` formulas, using only the
`PMcrd` header read by `read_pm_header` (`a_v = AEXPN - ASTEP/2`,
`100 Box/NGRID/a_v`), reproduces all 6 x 46656 int16 values of
`Subsample.0070.0001.bin` with zero mismatches; the 529-byte header dtype has
the right field order, kinds and offsets; the schedule and all 90 PowerDM
files parse identically to an independent parser. No Blocker or Major was
found. The Minor items are robustness/documentation traps: the half-step
`a_v` is silently wrong for `ic2pm sync` IC files, native PMP2start ICs are
split at 256 (not 512) records per file and are rejected with a misleading
error, `aexp0` is an uninitialised word presented as a field, the
"shell-averaged CIC window" is misnamed (37 % off the true shell average at
k_Nyq), and `mmap=True` fails on empty products.
Merge recommendation: **ready** (the Minor fixes can go in a follow-up or a
fix-up commit before the merge).

## 3. Verified OK

PMcrd header (snapshot.py `_FIELDS`, `_header_dtype`, `read_pm_header`):
- Field order and kinds match `write (4) HEADER, AEXPN, AEXP0, AMPLT, ASTEP, ISTEP, PARTW, TINTG, EKIN, EKIN1, EKIN2, AU0, AEU0, NROW, NGRID, Nrealization, Nseed, Om, OmL, hubble, Nparticles, extras` (tools:477-481) with Tools kinds `Character*45 HEADER` (:64), Real*4 `AEXPN, ASTEP, Om, OmL, hubble, Box` (:9-16), `AMPLT, EKIN, EKIN1, EKIN2, AEU0, TINTG, extras(100)` (:51-53), Integer*4 `NROW, NGRID` (:17-18), `iStep, Nrealization, Nseed` (:54), **Integer*8 `Nparticles`** (:31); `AEXP0, PARTW, AU0` are implicit Real*4 locals. Byte count 45 + 4x4 + 4 + 7x4 + 4x4 + 3x4 + 8 + 400 = 529; numpy dtype itemsize 529, offsets header 0, aexpn 45, aexp0 49, amplt 53, astep 57, istep 61, partw 65 ... hubble 117, nparticles 121, extras 129 (packed, no alignment padding).
- Single sequential record with 4-byte markers in this build: ifx defaults (no `-assume byterecl`, makefile:6-7), `-convert big_endian` swaps the markers too; the real files are 537 = 4 + 529 + 4 bytes and start with `00 00 02 11`. The marker-based byte-order detection distinguishes `>` (0x00000211) from `<` (0x11020000) unambiguously; a `PMcrs` file passed by mistake is rejected ("first record marker 3fe6ebc3 is not 529").
- `extras(100) = Box`: set in ic2pm.f90:197, PMP2start.f90:156, PMP2startMPI.f90:201, gadget2pm.f90:79; read back as `boxsize = extras(100)` (tools:320); no other `extras(` write in PMP2main's objects (`git grep "extras(" -- '*.f90'`). Real headers: only `extras[99]` non-zero (= 150.0).
- PMP2start's own header write (PMP2start.f90:704-706) has the same 22-item layout (`0.` in the `PARTW` slot).
- Parsed real values are sane: a = 0.2857143 at step 70, 0.6832941 at step 100 (checkpoint `PMcrd.DAT` and `PMcrd.0100.DAT` identical except `aexp0`), partw = 8 = 72^3/36^3, Np = 46656, Om/OmL/h as Setup.

PMcrs pages (`Snapshot`):
- `RECL = NACCESS = Nrecord*6` (tools:318, 447) in 4-byte units without `-assume byterecl` = 6 x 1024^2 x 4 = 25165824 B; real files are exactly 25165824 B; reader `record_bytes = 6*page*4`. Record content `Xb, Yb, Zb, VXb, VYb, VZb` (tools:525) = reader's `reshape(6, page)`; `velocities=False` reads the leading `3*page` floats, which are X, Y, Z.
- File split: writer opens a new file when `mod(i-1, Nrecpage) == 0 .and. i > 1` with `ifile = (i-1)/Nrecpage` (tools:494-497), i.e. pages 1..512 in file 0; reader `ip // 512` with 0-based `ip`. Names `PMcrs<i0>.<i4.4>.DAT` / `PMcrs<i0>.DAT` (tools:459, 468, 500, 502): the reader keeps the zero-padded tag captured from `PMcrd.(\d+).DAT` and builds `PMcrs{i}.{tag}.DAT`; checkpoint `PMcrd.DAT` -> `PMcrs0.DAT` verified on case11.
- Padding: the writer copies only `jfirst..jlast` into the buffers (tools:510-522) and writes the full buffers, so the tail of the last record is the previous page's content; the reader slices `[:, :n_in]` with `n_in = min(page, remaining)`. Exact-multiple case: Fortran `Npages = (Nparticles-1)/JPAGE + 1`, `NinPage = Nparticles - (Npages-1)*JPAGE = JPAGE`; reader `n_pages = (n + page - 1)//page`, last `n_in = page`. Same.
- Coordinates: writer stores grid units in `[1, NGRID+1)` (real ranges 1.0004..72.9997); `units='physical'` = `((X-1) Box/NGRID) mod Box` in float64 maps a particle at exactly `NGRID+1` to 0, the same periodic point `ReadDataPM`'s clamp `Xb - 1e-3` (tools:394-396) keeps inside cell NGRID for the CIC; the reader's treatment is correct for a reader, and `units='code'` is documented as "as stored". Real physical x range 0.0013..149.9993, none >= Box.
- `Snapshot.__init__` checks every `PMcrs<i>` exists and holds at least the needed records; `read(max_particles=...)` raises before reading.

Velocity epoch (`PMHeader.a_v`, `velocity_scale`):

## 4. Open questions for the author

1. `Nseed` in the header differs between outputs of the same run (1156811761 at step 70, 13979821 at steps 100 and in the checkpoint of case11): it is evidently the running RNG state, not the IC seed. Should `PMHeader` document that (and `aexp0`, R1-3) so nobody uses them as provenance?
