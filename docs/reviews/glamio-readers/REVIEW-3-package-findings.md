# REVIEW 3: the Python package as software (API, robustness, resources)

Branch `glamio-readers`, commit 0a6ecff (`cz..glamio-readers`), reviewed
2026-10-18. Scope: everything under `python/` as a library (glamio/*.py,
tests/*.py, pyproject.toml, README.md); not the Fortran. Method: line-by-line
reading plus small checks with the cosemu interpreter (`python3 -I`, `nice -n
19`, each a few seconds, < 300 MB) against the suite outputs in
`test/precise_z/work/case1{0,1,2}_*/Run1`, the pilot's
`LensPlanes.0057.0001` (201 MB), `OutputSchedule.dat` and
`PowerDM.R.0057.0001.dat`, and against synthetic edge cases written to a
temporary directory in the session scratchpad (removed). Interpreter: Python
3.14.2, numpy 2.4.3, `glamio` 0.2.0 imported from the main checkout's
editable install. No tracked file was modified, nothing was built or run
beyond these checks.

## 1. Summary

The package is sound as a reader library: every reader validates the sidecar
(product line, required keys, exact byte count) before touching the binary,
`mmap=True` really stays a memmap through `reshape`, `.T` and slicing, the
pure-Python logic I could test independently (`power()` against a brute-force
double loop, the Hermitian completion, `splitmix64` against a pure-Python
integer implementation, `select_ids` block independence, the 529-byte header
dtype) is correct, and the error paths raise `ValueError`/`FileNotFoundError`
with messages that name the file and the expectation. The three Major findings
are all resource guards for production-size inputs on a shared login node
(`Modes.power()` needs 9x the cube, ~4.7 GB for the n = 244 production
`deltam`; `Snapshot.read()` has no default cap and holds two copies, 52 GB for
a 1024^3 run; `Subsample.ids()` at M = 1 allocates `N_p` uint64 before
checking anything, 69 GB for 2048^3), not wrong results. The Minors are
robustness and consistency issues (empty products with `mmap=True` crash on
`np.memmap`, a false docstring about per-plane means, `read_modes` accepting
any sidecar with an `n` key, `product` returning the comment).
Recommendation: **ready after the listed fixes** (at least M1-M3 and m1-m3;
the rest can follow in a patch release).

## 3. Verified OK

- `_header_dtype`: itemsize 529 for both byte orders; offsets header 0 (S45), aexpn 45, aexp0 49, amplt 53, astep 57, istep 61 (i4), partw 65, tintg 69, ekin 73, ekin1 77, ekin2 81, au0 85, aeu0 89, nrow 93, ngrid 97, nrealization 101, nseed 105 (i4), om 109, oml 113, hubble 117 (f4), nparticles 121 (i8), extras 129 (100 x f4 = 400 B); 45 + 16 + 4 + 28 + 16 + 12 + 8 + 400 = 529. The real `PMcrd.0084.DAT` (537 bytes) starts `00 00 02 11` = 529 big-endian and is read with `bo = ">"`.
- `Modes.power()` equals a brute-force triple loop through `mode()` (pk, weights and k_mean, rtol 1e-10) for random complex64 cubes with n = 1, 2, 3, 4, 6, 9 and `nbins = n` and `2n` (empty bins `nan` in both). The Hermitian completion `mode(ix, iy, iz < 0) = conj(data[-ix+n, -iy+n, -iz])` and the direct half were checked exhaustively for every (ix, iy, iz) of those cubes: 0 mismatches. `mode(0, 0, 0) = 0` on the real `deltam` and `mom_x` cubes.
- On real output, `power()` of `case11 deltam.0084` (n = 11) matches `PowerDM.R.0084` for bins 1..11: pk within 2.8e-6 (the file prints 6 significant digits), weights exactly equal to the file's `N`, k_mean within 1e-4 (the file prints k with 5 decimals).
