# REVIEW 5: downstream impact, operations and repository hygiene

Branch `bdm-binary-catalogue`, commit 167fb1c (review range `cz..bdm-binary-catalogue`;
the branch also carries 1165ce4, the review prompts). Read-only review, 2026-10-18.
Everything below was checked against the code and the files on disk, not the prose.

## 1. Summary

The commit breaks no existing consumer as long as `CatalogueFormat` stays `text` or
`both`: every Fortran tool, halocat, `check_run.py` and `compare_hmf.py` open the
`.DAT` by its explicit name and ignore the new `.bin`/`.meta`. Four things need fixing
before the merge: (1) `gen_inputs.py` now always writes the `CatalogueFormat` key, and
every pre-merge `PMP2main.exe` (including the pilots' frozen `bin/` copies) rejects it
as an unrecognized parameter at the first catalogue step, about half-way through a
run; (2) `check_run.py` knows only the `.DAT`, so the documented switch to `binary`
makes it fail every run and in `both` mode the new files ship unverified; (3) the
storage figures in the plan mix allocated and apparent sizes and assume the binary
compresses like the text (Lustre compresses the text 1.93x, float32 about 1.1x), so
the on-disk saving is about a third of the quoted 4 GB per box and the default `both`
costs about +60 % allocated catalogue space on every BDM run of every campaign
directory; (4) the companion README tells the user to apply `a_v/a` while glamio and
the plan's Q3 apply `a/a_v`. Stale staged temporaries after a crash have no cleanup
and no documentation. Repository hygiene is clean (17 tracked files, no caches,
ignore rules effective); `Find BDM halos = 0` runs execute nothing new.

Recommendation: **ready after the listed fixes** (R5-01 to R5-04; R5-06 and R5-07
strongly advised before the first production campaign).
