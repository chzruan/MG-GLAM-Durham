# REVIEW 2: format specification and sidecar semantics — findings

Branch `bdm-binary-catalogue`, commit 167fb1c, reviewed read-only against the
code (PMP2linker.f90 `WriteFiles`/`GetHalo`/`FindDistinctCandidates`/
`SetOverdensity`/`RescaleCoords`/`SetParameters`/`WriteCatalogueMeta`,
PMP2main.f90 `MOVE`/`ADDTIME` and the main loop, PMP2mod_extras.f90,
python/glamio, test/precise_z/asserts.py) and against the LCDM pilot text
catalogue `CatshortV.0181.0001.DAT` (777,651 rows, read once with numpy).
Reviewer: Claude (Fable 5.1), 2026-10-18.

## 1. Summary

The binary record and the sidecar's machine-readable keys (`columns`, `dtypes`,
`units`, `rows`, `record_bytes`, `a`, `z`, `a_v`, `da`, `velocity_scale`,
cosmology, `particle_mass`, `MassMin`, `overdensity`) are consistent with the
Fortran write statement and with glamio's `CATALOGUE_DTYPE`; the velocity-epoch
claim `a_v = a - da/2` is correct for the PM loop, and glamio's `a/a_v` factor is
the exact conversion of the stored leapfrog momentum to km/s at `a_v`. The
text-precision analysis supports the `TEXT_TOL` tolerances. Two Major problems
are in the prose, not the bytes: (1) the sidecar's `centre =` line (and the
deck) define `Rvir` as the overdensity radius and `Mbound` as the bound mass
within it, whereas the code writes the Rext-extended aperture as `Rvir` and the
bound mass within the *unextended* SO radius as `Mbound` (in the pilot no row
has mean density within `Rvir` reaching Delta_vir; median 99 vs 338); (2)
DEGRACE-companion/README.md, plan section 3 and two deck frames state the
velocity offset with the inverted direction ("high by a/a_v, apply a_v/a") and
the commit now claims `velocities_at_av()` "does it", while the sidecar, glamio,
plan sections 11 and 16 (correctly) multiply by a/a_v. Minor items: storage
figures mix Lustre-allocated (compressed) and apparent bytes, the deck's
`MassMin = 1e11` is never the binding cut, the fR_halo sidecar names catalogue
files unconditionally, and a few unit/key inconsistencies between the text and
binary readers.

**Merge recommendation: ready after the listed fixes** (F1 and F2 are
one-line text changes in the Fortran sidecar and the prose; nothing in the data
layout needs to change).

## 3. Verified OK

- **Record layout.** The `write(CatUnitBin)` item list (PMP2linker.f90:702-705) is the 24 text items in the same order; every item is 4 bytes: `x,y,z,Vrms,rr,Cvir,aNpart,VirRat` are declared `real*4`, all arrays are `Real*4`, `1.e3*RadRms(ip)` is default real (the makefile has no `-r8`/`-real-size` flag), `int(iHalo,4)`, `0_4`. `CATALOGUE_DTYPE` itemsize 96, fields 12 (`row`) and 15 (`distinct`) are `<i4`, all others `<f4`, names in file order. The sidecar `columns`, `dtypes`, `units` lines each have 24 tokens and the `i4` positions match. `convert='little_endian'` on a stream OPEN is the same construct used by the fR_halo, LensPlanes, modes and subsample writers.
- **Column definitions from the code** (PMP2linker.f90): x,y,z = `xMaxx…` after `RescaleCoords` (`modulo(…,Box)`, clamp `>= Box → 0`) and four centre-of-mass iterations in `FindDistinctCandidates` (lines 1489-1540) — comoving Mpc/h in [0, Box) (pilot range 0.0005–1023.9999 ✓); vx,vy,vz = mean of the 1/a-scaled velocities of the bound particles (`bulk`, line 1211) in km/s; `Mtot = naperture·m_p`; `Rvir = 1e3·aperture` kpc/h; `Vrms = sqrt(2 EkinM/Mvir)` with `EkinM = ½ m Σ|v − v_bulk + H(a)·a·r|²`; `Vcirc = VmaxM = sqrt(G·max(q m/r_q)/a)/sqrt(1 − 0.1 cell/r_max)` km/s; `row = iHalo` 1-based (pilot: 1..N ✓); `Cvir` = NFW c from V_max/V_vir(aperture) via `Concentration`, fallback `2.1625816·Rvir/Rmax` when V_max < V_vir, 0 when unresolved; `Npart = Mbound/m_p` = membership count (pilot: `Mbound = Npart·m_p` to 4.8e-5 = text rounding ✓); `distinct = 0` always (pilot ✓); `Xoff = |⟨r − r_c⟩_bound|/aperture`; `virial_ratio = 2·EkinM/EpotM − 1` with `EpotM = Σ_q G m²(q−1)/(a r_q) > 0`, i.e. 2K/|W| − 1 as glamio's `COLUMN_UNITS` says (pilot range −0.88…1.71, 89 % negative ✓); `lambda` = Peebles spin with |E| ≈ K, dimensionless; `RadRMS = 1e3·sqrt(⟨|r − r_c|²⟩_bound)` comoving kpc/h; `b_a ≥ c_a` are the empirically corrected inertia-tensor axis ratios, `ax_*` the principal-axis unit vector.
- **Velocity epoch.** Main loop (PMP2main.f90:44-86): DENSIT → POTENT → `ASTEP` updated (exact-z: `ASTEP = dAlist(ISTEP+1)` with `FactV` spanning (da_old+da_new)/2) → `MOVE` (kick with `PCONST ∝ ASTEP·0.5/FactV` at `AEXPN`, drift with `XCONST` at `Ahalf = AEXPN + ASTEP/2`) → `ADDTIME` (`AEXPN = Alist(ISTEP)` / `AEXPN + ASTEP`) → `Analysis` → `BDM` last. So when BDM runs, positions are at `AEXPN` and the momenta at `AEXPN − ASTEP/2` with `ASTEP` the step just taken; `WriteCatalogueMeta`'s `a_v = AEXPN-ASTEP/2.` is literally the expression used by `ExtraModes` (PMP2mod_extras.f90:533) and the LensPlanes sidecar (line 197). `velocities_at_av()` returns `(N,3)` float64 = `v_written·a/a_v = ⟨V⟩_bound·100·Box/N_grid/a_v`: the exact unit conversion of the leapfrog momentum at its own epoch, not a first-order correction. (The legacy 1/a conversion implicitly treats V as if it were at `a`, i.e. free-streams the momentum over half a step; neither value is v(a), which would need the missing half kick, ~0.1 % at z = 0.)
- **Overdensity.** `SetOverdensity` returns `density` relative to the **mean** matter density for every `iVirial` (0: 200/Om(a) = 200 critical; 1: Bryan–Norman (178+82x−39x²)/Om(a); 2: 200; 3: BN·200/178), and `GetHalo` uses `threshold = (4π/3)·Ovdens·m_p·(N_row/Box)³` = Ovdens × mean density, so the sidecar text "(relative to the mean matter density at this epoch)" and the `iVirial` legend are correct. Pilot header `Overdensity limit = 338.3000` = the formula at Om = 0.3, z = 0 ✓; 203.4 at z = 1 ✓.
- **MassMin / selection.** Sidecar `MassMin` is written after `MassMin = max(MassMin, 20·MassOne)` (line 640, `WriteCatalogueMeta` called at 709), so it is the binding floor; rows pass `x,y,z ∈ [0,Box)`, `Mvir ≥ MassMin`, `Mvir > 0`, `aNpart ≥ 20` (lines 665-681). "rows also need Npart >= 20" is true (and implied by the floor). Pilot: min Npart = 20, min Mbound = 20·m_p ✓.
- **Text precision vs `TEXT_TOL`** (asserts.py:576-578), from `(3f11.4,3x,3f10.2,1p,2g12.4,g12.5,26g12.4)`: x,y,z `f11.4` → |Δ| ≤ 5e-5 (atol 6e-5 ✓; float32 ulp at 1800 Mpc/h is 1.2e-4 but the printed value is the correctly rounded decimal of the float32, so the bound holds); vx..vz `f10.2` → ≤ 5e-3 (atol 6e-3 ✓); Mbound, Mtot `1p g12.4`: always ≥ 1e4 → E form `d.ddddE±ee`, 5 significant digits (the `1p` adds one) → rel ≤ 5e-5 (rtol 6e-5 ✓); Rvir `1p g12.5`: F form for 0.1 ≤ r < 1e5 with 5 significant digits, E form with 6 above → rel ≤ 5e-5 (rtol 6e-5 ✓; atol 0 is safe, Rvir > 0); columns 10–24 `1p g12.4`: F form (0.1 ≤ |x| < 1e4) 4 significant digits → rel ≤ 5e-4, E form (|x| < 0.1 or ≥ 1e4) 5 digits → rel ≤ 5e-5 (rtol 6e-4 ✓), zero prints exactly (`0.000`, atol 1e-12 ✓), sign is irrelevant to |Δ|, integers print exactly (`Iw`). The pilot exercises the F/E switch heavily (E form in 76 % of `Xoff`, 98 % of `lambda`, 15 % of `virial_ratio`, 10 % of the axis components; 89 % of `virial_ratio` and a third of the axis components negative), so the tolerances are loose enough never to fail on a legitimate value and tight enough that any column swap, byte flip above the 4th digit or endianness error fails.
- **Sizes.** Pilot z = 0: 777,651 rows × 283 B + 636 B header = 220,075,869 B ✓ (file size); binary 777,651 × 96 = 74.65 MB ✓ ("75 MB", "220 → 75 MB", "3× smaller", "binary ⅓", "~0.12 GB" for a 0.35 GB text at 2048³, "≈ 4 GB per box at 2048³ … 0.75 TB over the suite" in apparent bytes) are arithmetically consistent; see F3 for the allocated-vs-apparent mix.
- **Naming.** `product = Catshort` // `CatLabelCur(1:1)` and `text_catalogue = CATALOGS/Catshort<label>.<step>.<box>.DAT` are label-aware (W/V/M/A for iVirial 0–3); `text_catalogue = none` when text is off. glamio takes the label from the sidecar (binary) or from the file name (`_PRODUCT_RE`, text) and assumes nothing about `V`; `read_catalogue` resolves `.bin`/`.meta`/`.DAT`/`.dat`/stem as documented. Only the fR_halo sidecar (F5), check_run.py and the test harness assume `V` (acceptable for the tests; `iVirial = 1` there).
- **README keys.** Every key python/README.md:27-29 lists (`columns`, `dtypes`, `rows`, `record_bytes`, `a`, `z`, `a_v`, `velocity_scale`, `step`, `Box`, `N_grid`, `N_row`, `Omega_m`, `Omega_L`, `hubble`, `particle_mass`, `overdensity`) is written by `WriteCatalogueMeta`; the Fortran additionally writes `product`, `format`, `units`, `text_catalogue`, `da`, `realization`, `MassMin`, `iVirial`, `buffer_width`, `centre`, `finder`, `header`, all covered by the README's "…" and by the plan/deck lists. `buffer_width` is the effective `dBuffer` after `PrepareParticleSearch` (15.375 Mpc/h in the pilot, same as the text header). `header` fits (`Character*45`, `trim`).
- **Text header parse.** glamio's regexes match the real pilot header lines 2–7 (`A =`, `Step =`, `I =`, `Nrow =`, `Ngrid=`, `Omega_0=`, `Omega_L=`, `hubble =`, `buffer width (Mpch) =`, `Mass of smallest particle (Msunh) =`, `Overdensity limit =`); `a_v = A − Step/2` printed to 6 decimals is adequate (the header's `f8.5` already limits `Step` to 5e-6, i.e. 2.5e-6 in a_v).
- **fR_halo sidecar `catalogue_bin` line** is syntactically a `key = value` line that `read_meta` parses; the row count check (`fR_halo rows == CatshortV rows == meta rows`) is unaffected.

## 4. Open questions for the author

1. Should the SO radius `r_SO` (or the particle count inside it) be added to the format now, while the binary layout is new? Without it the catalogue's only radius is the Rext-extended aperture, whose extension (up to 0.75 cells) depends on `Rext`, `SlopeR` and `N_grid` — none of which is in the sidecar.
2. Plan section 11 item 11 (1/a vs 1/a_v writer): if the writer is switched, `Vrms` and `lambda` must switch with `vx,vy,vz` (F7c); is that intended, and will the sidecar's `velocity_scale` then read `1/a_v`?
3. Which basis do the storage budgets use — apparent bytes (what `ls -l`, the plan's 220 MB and glamio see) or allocated blocks (what `du` and the Lustre quota see)? The merge rationale "saves ≈ 0.75 TB" halves on the allocated basis (F3).
4. The deck's "Definitions" frame describes the pilot cosmology (Omega_m = 0.3) as if it were general (F10); is the frame meant to be node-2 specific?
